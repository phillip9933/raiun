# Encrypted folders and Spaces: security review

Review date: 2026-10-06 (owner timezone). Scope: current vault-test.16 source, encryption compatibility, biometric key storage, offline files, explicit external-app handoff and cleanup. This is a focused source review plus regression tests, not an independent penetration test or certification. No claim of zero vulnerabilities is made.

## Pre-1.0 development review — 2026-10-13

This follow-up covers unpublished changes based on 0.9.3. The original review below remains historical evidence. Current acceptance gates and test results belong in [TESTING.md](TESTING.md); this review is not a penetration test or a guarantee that vulnerabilities are absent.

- Background upload staging stores only encrypted bytes and public destination metadata in private no-backup storage. Passwords, content keys, decrypted child names and plaintext digests are not durable worker inputs. Upload recovery conditionally writes the staged object and verifies its complete ciphertext before completion. A retry can replay the whole ciphertext; byte-offset upload resume is not implemented.
- Background offline downloads may resume only against the captured strong ETag with a checked byte range. Network completion is explicitly **awaiting unlock**, not offline-ready. A live password/biometric session authenticates the downloaded content before publishing an offline entry. This local verification can finish without a network connection. Account removal, cancellation and stale completion cannot publish a replacement transfer's result.
- Ordinary/encrypted and cross-encrypted copies pass plaintext through a bounded memory pipe. Their temporary traversal manifest is encrypted with a process-only key. Copying or moving out of encryption requires an explicit disclosure. Move verifies destination content and the complete source snapshot before any source deletion; later failures retain a partial-operation warning and do not automatically retry destructive cleanup. These operations require the unlocked foreground session.
- Review-driven fixes protect prepared transfer files from stale cleanup snapshots, prevent offline metadata from being recreated after account removal, discard late destination unlock results, and distinguish corrupt ciphertext from permission/network errors. Directory XML parsing rejects DTDs and limits structure and response size while avoiding a complete in-memory XML document.
- Favorite mutations now reject redirects and automatic connection retries. Basic credentials are encrypted before being saved together with one checked preferences commit. This preserves existing key names and does not migrate or replace the account's signing or encryption identity. A failed Android preferences commit is reported as a storage failure; it does not promise an in-memory rollback.

The public Maven inventory was queried against OSV on 2026-10-13: 165 packages, no reported advisories. This is limited to the inventory and OSV's available records; local scanner modules, native/model assets and build-time dependencies are outside that query. Dependencies did not change in this work.

Remaining engineering boundaries: directory listings still retain a validated typed result list and have a 32-MiB response safety cap; recursive encrypted offline pinning, scanner uploads and text saves remain foreground operations. Large-class cleanup extracted transfer recovery, ciphertext database operations and snapshot application into smaller units without weakening transactional checks. Further decomposition of the session/repository and UI state machines is a maintenance opportunity, not evidence of a vulnerability. Dependency verification metadata is also a future supply-chain improvement; no unreviewed trust-on-first-use checksum set was added.

## Release-candidate review fixes — 2026-10-14

The combined candidate review found two release-relevant issues: fragmented SAX text callbacks could evade the per-response DOM node bound, and a cancelled encrypted offline transfer could retain a published copy before its transfer row completed. The parser now coalesces text in a bounded builder and counts text as well as element nodes. Offline publication retains the prior encrypted metadata until completion is accepted; rejection restores the previous verified copy without recreating removed-account data.

Background publication also records a bounded recovery journal containing prior encrypted metadata, public root identity and opaque job/blob identifiers. It contains no vault key or decrypted child filename. Recovery consults the durable transfer outcome before keeping a replacement or restoring the previous snapshot. Recovery must run before opening or changing affected offline data and before removing transfer-history evidence. Unreadable recovery data or storage failure must fail closed and retain recoverable ciphertext rather than silently claim cleanup succeeded.

Cancellation state belongs to live attempts rather than a permanent set of cancelled IDs. The UI retains upload-notification state across scanner navigation; queue tests distinguish background handoff from foreground upload. A related same-ID offline retry observer ordering issue was also corrected. Verification results for this follow-up are recorded in TESTING.md; these implementation notes do not establish physical-device acceptance or a security certification.

## Historical process-only phone-unlock candidate — 2026-10-28

This implementation is superseded by the explicitly selected device-remember candidate below; the description records the earlier behavior.

The default local policy can reuse an already verified location key while the phone remains awake and unlocked with a secure screen lock configured. It does not derive a vault key from the phone's PIN or replace the first password/biometric unlock. **Ask every time** disables reuse. The existing biometric envelope and auth-per-use Android Keystore requirements are unchanged.

The cache holds at most eight defensive copies of the compatible 80-byte key bundle, in process memory, bound to the full account/server/drive/root identity, an immutable account snapshot and a credential-revocation lease. Eviction clears the owned bytes. Route exit and ordinary backgrounding still close the active route session, previews and operation permits; cached-key reentry obtains a fresh repository session, account/access checks and online password proof or authenticated offline-manifest proof. Caching a key does not authorize a different location or a background plaintext operation.

The process-global screen-off receiver revokes remembered access even when no encrypted route exists. Explicit location lock, credential replacement/removal and biometric preference reset invalidate relevant grants. Policy changes clear the cache. Generation checks reject late authentication/admission after revocation; device/policy lookup failure also clears cached grants. A normal OAuth token refresh does not extend or revoke the phone-unlock session. Process death drops all temporary keys. The saved setting is a boolean, not a password or key. Android's [device-lock APIs](https://developer.android.com/reference/android/app/KeyguardManager) distinguish a configured secure lock from current lock state; the implementation also requires an interactive display and conservatively revokes on screen-off.

This deliberately extends how long a verified key may remain in Raiun's memory. The stronger option is Ask every time. Owned-buffer clearing is best-effort, and the managed-runtime/platform memory limits below still apply. Host regressions and a separate source review target cache binding, proof, disposal and revocation races; current execution results belong in [TESTING.md](TESTING.md). Physical lifecycle and biometric acceptance remain separate.

## Device-remember candidate — 2026-10-29 (unpublished)

The owner chose the existing question to mean **Remember on this phone**, including app restarts and later phone unlocks. This is new explicit per-location consent after fresh password/biometric proof; old biometric consent is not automatically migrated. The encryption password is never persisted. The exact 80-byte verified key bundle is encrypted using a separate AES-256-GCM Android Keystore key and an atomic app-private no-backup record. Existing per-use biometric aliases and envelopes remain unchanged.

Durable remembering requires API 35+, a secure lock, current unlocked/interactive state, and verified TEE/StrongBox backing. The key is created with `setUnlockedDeviceRequired(true)` and no timed/per-use authentication window. Android documents issues on earlier versions; unsupported devices retain fresh password/per-use biometric access. Public KeyInfo fields are checked. The unlocked-device getter is absent on API 35, so that platform's documented creation contract is used for freshly generated aliases; an exposed false getter or invocation failure rejects the key. This is not an attestation claim.

Identity, account incarnation/digest, crypto profile, nonce, alias and durable revocation epochs bind each record. Every entry unwraps through the durable store and obtains fresh online/offline proof under existing credential and app-lock permits. No RAM cache authorizes a bypass, and no background worker receives a key. Strict policy and its revocation fence commit under the same lock; explicit credential replacement/removal revokes while ordinary token refresh does not. Ask every time removes remembered access while preserving declined-choice markers. Settings reset removes selected access and allows the consent question again.

Screen-off closes live decrypted sessions; the record remains usable after a later phone unlock. Explicit location Lock shows a pending state until durable revocation finishes and reports failure rather than claiming success. A pending operation interrupted by actual process death is not a completed revocation. Unknown enrollment cleanup blocks same-process reuse until a new durable forget succeeds. Unreadable/corrupt/mismatched data fails closed. Old complete valid snapshot replay is not prevented by ordinary filesystem epochs, and root/OS compromise is outside this protection. Removing and re-adding a screen lock while the app is dead is not promised to destroy a non-auth-per-use key; access is denied while no secure lock is configured.

Source review and current test results are recorded in [TESTING.md](TESTING.md). These checks do not establish physical OEM Keystore behavior, forensic erasure or security certification. See Android's [unlocked-device key requirements](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUnlockedDeviceRequired(boolean)) and [KeyInfo](https://developer.android.com/reference/android/security/keystore/KeyInfo).

## Protection and evidence

- The compatible rclone-crypt profile uses scrypt (N=16384, r=8, p=1, default Web salt), AES-EME for names, and XSalsa20-Poly1305 SecretBox for content. Each 64-KiB block is authenticated before its plaintext is emitted; nonces use SecureRandom. The 80-byte key bundle is copied defensively and explicitly cleared on session close. Existing Web-v8 and rclone known-answer tests check both directions and boundary sizes; wrong-key and altered-block tests reject content. See `core/crypto/RcloneVaultCipher.kt` and its host/native tests.
- Biometrics wrap the key bundle using AES-GCM and Android Keystore keys. Strong biometric authorization is bound to the actual cipher operation, not just a successful UI callback. Hardware enforcement is checked; unsupported devices fall back to password entry rather than weaker key storage. Associated data binds the envelope to account, server, drive and encrypted location. Biometric enrollment changes invalidate the wrapping key. Password recovery remains essential; this convenience is local to the phone.
- Offline contents remain original ciphertext. The encrypted manifest uses an identity-bound HKDF-derived AES-GCM key and stores the blob digest and expected length. Loading rejects changed blobs, wrong keys and cross-identity manifests. Account removal/revocation invalidates existing access. Public root descriptors and previously seen location labels remain available for navigation: the existence, root label and location identity are not hidden by the vault encryption. Child names/content require unlock.
- Internal image/PDF/text previews decrypt in memory, without creating the external-app plaintext files. Large previews and thumbnails use independently authenticated AES-GCM chunks in private cache, with a random key kept only in RAM; chunk position and length are authenticated. Closing the preview clears the key and removes its ciphertext cache. Interrupted ciphertext caches are removed on the next preview initialization. Large text editing streams unchanged ranges around a bounded edited section, retaining the existing issued-entry and ETag checks. Encrypted edits are volatile. Closing/locking drops session keys and sensitive preview state. Explicit byte-array clearing reduces exposure, but managed-runtime strings, UI bitmaps and third-party native buffers do not provide a guarantee of complete RAM erasure. A compromised/rooted OS or an app running with Raiun privileges is outside this boundary.
- Online reads check the issued source, current account/session, expected ciphertext length and available strong ETag. Short/changed transfers are rejected. This is additional transport/change detection, not a cryptographic proof that the server has never replayed older content.

## Open with: deliberate plaintext handoff

After a warning and explicit acceptance, Raiun creates a decrypted file in private no-backup storage. It gives the selected app a read-only grant through a non-exported provider using an opaque UUID URI. Registry/path validation rejects invented paths and write access. Before launch, the VM checks that the account, session, source and route generation still match. Failed and cancelled exports never receive a published lease.

Raiun attempts deletion and grant revocation on return/navigation. A monotonic ten-minute expiry denies new provider opens independently of the wall clock; WorkManager schedules physical cleanup, and startup removes interrupted exports. Test16 adds retry scheduling for failed deletion of partial exports, plus fail-closed export storage when startup cleanup cannot finish. An export-storage error no longer prevents the rest of the app from starting. Failed scheduling/storage operations can still require a later successful startup before physical deletion completes.

This file is plaintext while it exists: it is no longer protected by the vault password. Android sandbox/device storage protections apply. Deletion unlinks Raiun’s file; it is not guaranteed forensic erasure from flash. Android can delay background work, especially during force-stop or power restrictions. Ten minutes is a deadline for **new URI access**, not a guarantee of physical deletion at that instant. A receiving app can retain an already-open descriptor, save another copy, share it or back it up. Raiun cannot erase those copies. Use the internal viewer when this disclosure is unacceptable.

## Format limitations preserved for Web compatibility

The rclone format authenticates individual content blocks, not a complete file/path/version manifest. Filename encryption is deterministic and is not authenticated; file lengths, directory relationships and server metadata remain observable. A malicious server with control of both ciphertext and advertised metadata can replay valid older ciphertext, substitute a valid same-key file, or remove complete trailing blocks without violating those remaining block tags. Expected-length/ETag checks detect inconsistent transport or stale operations, not every malicious metadata rewrite. Strong, unique encryption passwords matter because an attacker with ciphertext can perform offline password guesses. These are limitations of the compatible format, not promises that Raiun can remove without changing interoperability.

### Bounded operation and transfer follow-up — 29 October 2026

Boundary operations now validate complete streamed directory metadata while retaining only an exact target or presence result. File descriptors still match the captured ID, path, name, size, version and content type; malformed late entries cannot be ignored after an early match. Operation-scoped entry tokens survive unrelated UI paging and destination writes, are consumed for their mutation subject and are removed on callback exit or session closure. Directory deletion retains its complete empty proof and conditional version check. Ordinary post-delete checks also notice a replacement encrypted marker and never delete that replacement.

Source review identified the underlying rclone engine's whole-stream synchronized monitor as a same-session pipe deadlock risk. Boundary source/readback and destination streams now use independent in-memory content-cipher instances, closing each in `finally` and wiping the temporary exported key buffer. This avoids holding one cipher monitor across both ends of a bounded pipe; it does not add persistent keys or allow locked workers to decrypt. API 26 and API 35 synthetic loopback regressions using the actual engine verify a larger-than-buffer round trip, exact-descriptor refusal and stalled-transfer cancellation. Managed/native memory clearing remains best-effort.

Retained-transfer bulk actions use account-incarnation and queue-admission guards inside retry admission, preventing a removed/recreated account or a newly retried row from joining an older action. Ordinary file preparation also rechecks its original path/kind/ETag and app-action permit after waiting for a download. These are focused local regressions, not evidence of live-server compatibility or a whole-codebase security certification.

### Recursive operation snapshots — overnight Phase 3

Recursive transfers now capture each directory into an independent encrypted metadata stage before returning any child to the copy loop. The stage contains descriptors, not actionable page tokens or unlocked vault keys. Disposable AES-GCM and HMAC keys bind records to their sequence and identity/path indexes. Strict field framing, UTF-8 validation, duplicate ID/path refusal, frozen counts and contiguous sequence checks prevent malformed/truncated stages from becoming successful shorter listings. Page and lookup delivery recheck cancellation, source account/session ownership and closure outside database cursors/locks. Failure or cancelled delivery closes only the owned stage and clears its keys; deletion and managed-runtime erasure remain best-effort.

The final move barrier compares complete fresh source and destination child sets through keyed lookups and exact counts, including empty directories. It preserves exact file tuples, the existing directory identity policy, strong conditional mutations and full readback verification. No source deletion starts before that whole pass succeeds. Later cleanup can still become a partial move if the server changes or connectivity fails; Raiun does not blindly replay deletion or remove an unowned partial destination. This is not an atomic remote tree snapshot or a durable delete-recovery journal.

Focused corruption, late metadata failure, cross-batch hidden-child, version/MIME substitution, guard/cancellation and cleanup regressions accompany the change. Android-native checks cover the actual SQLite/JCA store and a real vault stream/name-decryption/store integration before the native content pipeline. Destination chooser/name-planning collections, temporary-copy cleanup, offline-manifest capacity and conditional upload finalization remain separate boundaries. See [TESTING.md](TESTING.md) for executed counts and physical/live-server limits.

### Destination name reservations — overnight Phase 4

Name planning now validates the entire destination directory once before publishing an operation-private membership index. It stores only fixed-size HMAC-SHA256 tokens under a disposable in-memory key. Strict incremental UTF-8 hashing preserves case and Unicode distinctions, rejects malformed surrogate input and avoids a name-sized encoding buffer. Atomic reservations match the earlier Set behavior, including duplicate names and selected-item collisions. Ordinary encrypted-marker names are included without readable file descriptors. Guard/cancellation/closed checks surround capture and reservations outside database locks; owned storage and key material are cleared on failure or closure.

The index closes before the conflict popup, all-source preflight and any copy. Keep both obtains a fresh index. It supplies naming hints; conditional server creation, exact source checks, full readback and deletion proofs retain authority. The row-count guard detects missing/extra membership rows, while arbitrary same-count private-table rewrites are outside that guarantee. The selected request and chosen-name plan remain proportional to the selection. Destination chooser paging and temporary-copy maintenance remain separate work.

A full native run revealed an ordering assumption in the cancellation fixture: deliberate permission revocation could correctly return AccessDenied before cancellation reached its child coroutine. ### Local offline index continuation — 29 October 2026 (unpublished)

The RVO2 metadata format replaces the aggregate 16-MiB plaintext map. Immutable SQLite generations store bounded ciphertext chunks and HMAC path tokens. AEAD binds each record to exact identity/location, generation and sequence; the encrypted root seals complete ordered membership and count. Full scans, including failed/missing lookups, validate the whole generation before results are used. SQL projects bounded BLOB slices before materialization. Generation/purpose keys are derived from the existing master; record nonces are unique by sequence under each generation key. Strict UTF-8 handling preserves valid Unicode and rejects lossy input. A complete prior valid snapshot can still be replayed; no trusted anti-rollback counter is claimed.

Read-only legacy opens preserve RVO1. Successful mutations import authenticated legacy metadata without changing the original ciphertext or key identity. This is forward compatibility for the new reader, not support for downgrading to an old binary. Canonical path confinement precedes writes/deletion, and active generation/blob leases prevent premature cleanup. Local v3 PREPARED/COMMITTED decisions are distinct from legacy Room-authorized transfer journals. Backup-only metadata, failed writes, accepted cancellation and ambiguous commit synchronization are covered by focused regressions; ambiguous states keep recovery evidence and both sides. Directory fsync invocation does not prove complete Room/filesystem power-loss atomicity or hardware durability.

Ordinary temporary cleanup now uses frozen full descriptors on private disk and scoped account/row CAS. OS leases protect active staging; cache-use, pin, ancestor, active-download, path/size and age checks remain authoritative. Host fixtures use real JVM directory synchronization because Robolectric cannot open directories through ShadowLinux; native tests exercise the actual public Android fsync path. Exact full-candidate results are recorded separately in TESTING.md. Durable encrypted offline groups, server-conditional upload continuation and physical deployment acceptance are not claimed delivered by this metadata slice.

### Combined offline groups and maintenance — 29 October 2026 (unpublished)

The subsequent candidate implements durable whole-folder/Space offline groups. Capture requires a live unlocked session; complete private plans are sealed before admission. Background workers receive opaque identities and transfer ciphertext without unlock keys. A later unlock authenticates the full plan, child jobs, actual payload lengths and rclone blocks, and the ordered checkpoint commitment before a strict-base offline refresh/prune. A source tree is a set of complete observations, not an atomic server snapshot. A changed local base requires a new capture rather than an unchecked merge.

Room schema 27 binds group work to the current account incarnation and exact parent/revision/attempt/work ownership. Publication reserves an independent receipt before filesystem changes; v4 journal recovery uses its durable decision and retains ambiguous evidence. Revocation, rejected completion, cancellation and history removal do not silently authorize a new root. Existing readers wait for committed-root recovery, and terminal member history is compacted only when no parent or unresolved publication remains. This extends scoped recovery; it does not establish joint Room/filesystem power-loss atomicity or protection against replay of a complete valid old snapshot.

Explicit ordinary local-copy removal now also uses a frozen disk-backed scope. Exact rows, account incarnation, pin choices, download admissions, reader/writer leases and owned paths are rechecked before deletion. Later completed downloads remain protected by an admission watermark; clearing transfer history invalidates old removal scopes. The cache-use gate precedes the Room transaction. Unsafe paths, changed copies and busy readers are retained with localized feedback. These local deletion operations are not a filesystem/database crash transaction.

Prepared file downloads use a strict single-resource Depth0 DAV request with a 2-MiB response budget. The complete tail is validated before GET; extra, missing or malformed responses cannot fall back to an optimistic match. This does not bypass complete root/account/source-version proofs or the separate root-listing budget. Servers that ignore Depth0 can still impose wide-root latency.
