# Encrypted folders and Spaces

This guide describes the encrypted-vault features included in the published Raiun Android 1.0.0 release, plus their security and interoperability boundaries. Historical implementation plans and test notes remain historical records; current validation evidence is maintained in [TESTING.md](TESTING.md).

## Local follow-up (unpublished)

The current candidate pages online and offline encrypted directories through temporary, encrypted, process-keyed sort storage. Names are decrypted in bounded batches; only the current page receives action leases. Hidden filtering and global folder/name ordering precede paging. Navigation, refresh, lock and account changes revoke old pages. Complete streamed metadata validation finishes before a directory becomes visible. The offline metadata follow-up replaces the single 16-MiB map with authenticated immutable disk generations. A small encrypted root seals their complete count and ordered membership; reads validate the full chain before issuing results. Aggregate metadata is no longer capped at 16 MiB. Individual metadata records remain bounded, independently of file-content size.

RVO1 snapshots remain readable and are imported on a successful mutation without rewriting their ciphertext blobs or changing unlock keys. Read-only legacy access leaves the old format unchanged. This is a forward local-metadata migration: older clients cannot read RVO2, and older app builds cannot open the Room schema 27 database. No downgrade path is promised. Generation/blob readers retain their content until release. Local commit records distinguish prepared and accepted foreground updates; transfer publications retain their Room authority. Directory synchronization protects new file references, but local checks do not establish a complete Room/filesystem power-loss transaction.

Scanner outputs and text edits join the ciphertext-only background queue after encryption finishes while unlocked. A text replacement captures the issued file's strong ETag and exact encrypted path; it cannot silently overwrite a newer version. “Queued” means accepted locally, not saved on the server. A scanner batch admits each output separately: discarding later pages does not cancel already queued transfers. Whole-folder and Space offline capture prepares a complete, immutable group while the live unlock is available. Once admitted, its background worker transfers ciphertext without an unlock key. A later live unlock verifies every prepared member and publishes one refreshed offline snapshot; the previous copy remains until that publication is accepted. If the account or preparation grant is revoked before admission, preparation stops.

These are local source changes, not a published release or a physical-device acceptance claim. Byte-offset upload continuation remains disabled until the server can enforce destination conditions through durable commit.

## Android 1.0.0 transfer behavior

Picked-file uploads are encrypted locally while the location is unlocked, then scheduled using only ciphertext. Once preparation finishes, the network upload can continue after locking or process restart. Recovery checks for an already committed identical ciphertext before retrying a conditional write. Upload retries can resend the complete staged ciphertext; this does not claim byte-offset upload resume or unsafe overwrite-based finalization.

Individual files selected for offline access can download ciphertext in the background. A matching strong ETag permits byte-range continuation; without one, the download starts again. Download completion alone is not offline readiness: the file stays pending verification until a matching live unlock authenticates all its encrypted content. A protected empty root manifest established at selection allows that verification on a later offline unlock, without storing the password or unlocked key material. Existing valid offline copies are preserved until replacement succeeds.

Copy and move can choose another ordinary or encrypted location in the same account. Crossing into ordinary storage requires confirmation because the destination contains plaintext. Transfers requiring decryption remain bound to live unlocks and stop on lock/background or process death. Moves verify copied contents and source/destination snapshots before source deletion; a partial cleanup is reported rather than replayed automatically. Conflicting names offer Cancel or Keep both, and conditional writes still protect against races after the choice.

Prepared-download preflight uses a depth-zero WebDAV request for the exact file and its metadata; this removes the per-file parent listing when the server honors the requested depth. It does not replace the encrypted-root validator, which still consumes and validates the complete DAV response with its existing 256-MiB limit. A server that ignores depth zero can still return every root child. The direct stat is only a prepared-download metadata check and does not prove directory completeness or authorize mutation. Generic encrypted-upload byte-offset continuation remains disabled until durable conditional finalization is verified for the server. The protocol format and external-app handoff limitations below remain unchanged.

## Android 1.0.0 feature scope

Raiun recognizes encrypted folders and encrypted Spaces in the normal Files and Spaces surfaces while keeping them outside ordinary plaintext file queues and caches. Users can unlock with a vault password and, where the device enforces strong biometrics through Android Keystore, opt into biometric key access. Password recovery remains necessary. The feature targets the OpenCloud Web rclone-crypt profile; it does not guess alternate rclone modes.

The release includes online browsing and internal text, image and PDF viewing; encrypted text editing; encrypted folder scanning; same-vault file operations; encrypted-location management; and offline snapshots. Picked-file encrypted uploads and individual encrypted-file offline downloads run in background after preparation/selection. Copy and move can cross between ordinary and encrypted locations, with confirmation before a destination receives plaintext. Secure scanner output is temporary app-private data. The unpublished follow-up encrypts it under the live session before admitting a ciphertext-only background job; no plaintext scanner output or unlock key becomes durable worker input. Offline snapshots store ciphertext and protected metadata. External-app opening is an explicit plaintext handoff with a warning, read-only URI grant, bounded new-access lifetime and best-effort cleanup.

See the dated [testing record](TESTING.md) and [security review](ENCRYPTED-SECURITY-REVIEW.md) for retained evidence and limits. Historical checks are not claims that those checks were rerun for this documentation update, and automated evidence is not a security certification or a guarantee for every OpenCloud installation, Android device or external app.

## Interoperability contract

The target is the OpenCloud Web v8.0.0 rclone-crypt profile used by OpenCloud 8.0.1: scrypt `N=16384, r=8, p=1`, 80 derived key bytes, AES-256 EME encrypted names, and `RCLONE\0\0` content files with 64-KiB XSalsa20-Poly1305 blocks. The integrity UUID property is used as password proof only when it contains nonempty authenticated content. Android streams blocks and authenticates each complete block before exposing its plaintext.

The codec has independent Web and rclone interoperability fixtures. The code supports the compatible profile only. Non-default password2, alternate filename modes and alternate encodings are not supported. Other OpenCloud/server versions and administrator-customized Web deployments require separate compatibility verification.

The format authenticates content blocks, not the complete file, path, final length or version. It cannot by itself detect every rollback, whole-block tail removal or valid same-key file substitution. Names and metadata such as file sizes, timestamps, hierarchy, root labels and membership may remain visible. Do not describe ETags or offline manifests as protection against a malicious server rewriting all associated metadata.

## Protection boundaries

Vault passwords derive encryption keys locally and are not sent to the server by Raiun. OAuth credentials separately authorize server operations. Existing biometric access wraps derived key material with Android Keystore and requires strong hardware-backed biometric authorization for each unwrap. The unreleased **Remember on this phone** choice instead uses a separate hardware-backed AES-GCM key requiring the phone to be unlocked, on Android 15 or newer with a secure screen lock. It stores an encrypted verified key bundle in no-backup storage, survives app restarts and permits access after later phone unlocks. Old biometric consent is not silently converted. **Ask every time**, explicit location Lock, access reset and account removal revoke device-remember access; ordinary screen-off closes live decrypted sessions without deleting that choice. Reentry still creates a fresh checked online/offline session. Unsupported devices retain fresh password/per-use biometric access. The encryption password is not saved. Buffer clearing is best-effort and does not guarantee erasure from managed-runtime memory or platform rendering buffers.

Offline data contains encrypted file blobs and identity-bound protected metadata. Root existence and labels can remain visible for navigation. Removing a server share cannot revoke keys or copies that a user already obtained. Local deletion unlinks files but is not forensic erasure from flash storage.

An external app can read the plaintext copy during the handoff and can save, share or back it up. The bounded URI expiry denies future opens; Android cannot revoke an already-open descriptor or erase a recipient's copy. Use internal viewing when external plaintext exposure is unacceptable.

## Remaining feature boundaries

- Encrypted folder/Space preparation and operations requiring decrypted content need a live unlock. Prepared whole-folder transfers can continue as ciphertext-only background work, but completion is not offline-ready until a later live unlock verifies the complete group and accepts the atomic refresh. Generic byte-offset encrypted-upload continuation remains disabled.
- Public links, per-child sharing, encrypted DocumentsProvider access and server-side Office editing are not included.
- Upload retries may resend complete staged ciphertext; they do not provide byte-offset upload resume. Encrypted downloads resume by byte range only when a matching strong ETag is available; otherwise they restart. Download completion requires later authentication during unlock before content is treated as available offline.
- The local metadata format is forward-only for older app builds: RVO2 and Room schema 27 cannot be read by earlier versions. Existing encrypted files and unlock keys are not rewritten, but no database downgrade is promised.
- Alternate rclone profiles, password rotation/re-encryption and account-token storage migration are unsupported. The compatible profile does not imply compatibility with every server version, and the source review is not a formal security audit.

Raiun's encrypted-vault security review records format limitations and the external handoff boundary in more detail. Public protocol references include the [rclone crypt format](https://rclone.org/crypt/) and [OpenCloud Web v8.0.0 vault implementation](https://github.com/opencloud-eu/web/tree/v8.0.0/packages/web-app-rclone-crypt).
